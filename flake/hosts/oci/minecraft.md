# MC 服务器/客户端 Mod/数据包筛选与滚动更新标准

**版本**: v1.7 final　**日期**: 2026-09-28　**范围**: NeoForge/Fabric 生态 + vanilla 数据驱动内容，Modrinth+CurseForge 为主索引，**服务端与客户端适用同一套必要条件**

**目标**（终局标准，不是过程标准）：让服务器/客户端尽量贴近 Mojang 最新版本做滚动更新，同时最大化装入跟得上这个节奏的 mod/数据包（效能+玩法都要）——**不为保留某个特定项目牺牲版本新鲜度**。

> **阅读约定**：本文 §-1–§10 是规范性内容，只描述抽象判据和类别，**不点名任何具体 mod/事件/工具链**——判据要在任何时间点、任何具体生态状态下、任何具体部署方式（Nix/手动/其他打包工具）下都成立。所有具体产品名、版本号、历史事件、部署细节都集中在文末 **§11 附录（非规范性示例）**，并标注日期与来源——附录内容会过期，每次实际筛选前必须重新核验。
>
> **适用范围声明**：本标准验证的是"候选是否值得被选入、以及选入后的批次是否能实际跑起来"这一层——具体覆盖 metadata 核验（条件1-5）+ 批次实机启动验证（§5.1）。它**不覆盖**、也不可能覆盖：特定硬件/GPU驱动/显示合成器（compositor）层面的渲染相容性、以及具体部署/打包工具链本身的实现细节（这些是执行环境问题，不是候选选择问题，见 §3 边界条件）。

## -1. Project Type 分流（在 loader 决策之前）

**这一步决定候选项目要不要进入 §0 的 loader 决策树，是比 §0 更早的分支点。**

判据的机制基础：vanilla 的数据驱动注册表（loot table、recipe、tag、worldgen、function/predicate/item modifier）由游戏引擎本体直接解析，不经过 loader 的代码注入层——数据包/资源包的加载路径与是否安装某个 loader 无关。这不是简化假设，是架构事实。

| project_type | 是否进入 §0 loader 决策 | 版本匹配判据 |
|---|---|---|
| 纯数据驱动内容（数据包、资源包、光影包等，只用 vanilla 数据格式，无绑定代码） | **否**——loader 字段对它不携带信息 | 只查 `game_versions`（对应 pack_format）是否覆盖目标版本，loader/platform 字段忽略 |
| 代码类（mod、服务端插件等，含编译逻辑/字节码注入） | 是——走 §0 完整决策树 | 走 §5 条件1原版判据（含 loader 过滤） |

**关键限定（不能反过来推广）**：
1. 一个项目**同时**列出"纯数据驱动"和某个真实 loader/平台，说明它存在绑定代码的变体。此时只有确认为纯数据驱动的那个具体版本可以走左列判据，**不能因为项目本身被归类过就整体免检**——回到条件4的递归依赖检查里，看它是否声明了对某个 mod 的 required 依赖。
2. 纯数据驱动的判据本身受结构性限制约束：无法新增注册表 ID（新方块/物品类型）、无法自定义渲染逻辑/GUI。§0 中"玩法向以多方块/机械类内容为主 → 需要 loader"这条判断**不受本节推翻**——本节只是把候选池里真正 loader 无关的子集单独摘出来。**这也是它的实际价值所在**：当某个"必须要 loader"的内容类 mod 拖慢了追新节奏时，先检查有没有功能相近、纯数据驱动的替代品可以在不牺牲版本新鲜度的前提下顶替（案例见 §11）。
3. 已知的平台层坑：部分索引/客户端工具会把"纯数据驱动"当作外来 platform 类型来处理，从而产生虚假的"不兼容"判定。筛选流水线**必须直接查询原始 `game_versions` 字段**，不能复用任何工具衍生的"兼容/不兼容"标记。
4. **"无编译代码"不等于"不需要查源码链接"**（见条件5、F29）——这是两件不同的事，条件5的要求不因项目是纯数据驱动就放宽，见 §5。

## 0. 前置决策：loader 选型（仅适用于经 §-1 分流后判定为"代码类"的候选）

### 0.1 执行纪律（先于任何具体判断）

- **规则A：每次执行本标准都要重新推导，不能沿用旧结论。** 即使重新推导后结论文字不变，也必须重新走一遍论证链（对应 F21）。
- **规则B：架构层面的论证只是先验方向，不是最终裁决。** 真正拿不准、或利害关系大的场景，必须先分别把 §5 全部必要条件在**两边生态各自的候选池**上完整跑一遍，产出两份独立的通过清单，用清单里实际的数量、质量做比较（对应 F22）。

### 0.2 场景先验（仅供启动时参考，最终判断按 0.1 规则B 执行）

| 场景（类别） | 先验方向 | 原因（类别层面） |
|---|---|---|
| 玩法向以多方块/机械类内容 mod 为主 | 保留目标 loader 生态，**松动条件3的滞后阈值**，不要动 loader | 这类内容 mod 的生态可能集中在某个特定 loader 系；若该 loader 系的 API 表面积更大，天生比精简架构的 loader 移植更慢——这是**结构性**滞后，比任何单个 mod 的滞后都大 |
| 主要是性能优化+轻量玩法调整 | 优先选择该发布周期内追新更快的 loader | 精简架构的 loader 通常能更快跟上新版本；"哪个 loader 更快"是会随生态变化的事实，不写死进规则 |
| 两者都要 | 引入一个"跨 loader 兼容层"类 mod，**该兼容层本身也要作为一个依赖，过下面第1–5条** | 兼容层不是免费午餐——它自己会有兼容性 bug、会被目标 loader 误判不兼容 |
| 玩家群/存量内容已锁定某个 loader，无法更换 | 保留该 loader，接受"loader 自身滞后 + 规则滞后"叠加的真实 SLA | 显式承认，不要假装能做到比 loader 本身更快的追新速度 |

## 1. Acceptance Criteria（可核验，不靠判断）

一次筛选流程的产出被判定为"合格"，当且仅当同时产出以下四份可审计记录：

1. **通过清单**：每个候选附带它通过的条件编号（§-1 分流结果 + 1–5必要 + 6–8加分分数），标注维护者/工作室归属（供 §3 集中度检查用），并标注是否已完成 §5.1 批次实机验证
2. **拒绝清单**：每个被排除的候选，附带**具体是哪一条规则**（编号）判定失败，及该判定所依据的原始数据（API 返回值，非转述，非工具衍生的兼容性标记，非未过滤的"最新版本"字段）
3. **未发现候选估计**：用 §8 的参照集抽样方法给出的召回率缺口估计
4. **批次实机验证结果**（§5.1）：本轮变更是否已实际启动过、有无异常——这一项不能用"条件1-5都通过"来代替，两者验证的是不同的东西（见 F26、§5.1）

任何一次筛选如果只产出前三份而跳过第4份，或反过来只做了实机测试没有可查证的清单，都视为**不合格的流程输出**。**声称"已完成/已记录"但无法在实际存储位置查证到的产出，视为未完成**——这条是从本标准自身的执行事故里加回来的（见 §9）。

## 2. Key Definitions（锁死歧义词）

| 术语 | 锁定定义 |
|---|---|
| "纯数据驱动内容" | project_type 为数据包/资源包/光影包类，且不存在绑定编译代码的变体；判据见 §-1 |
| "大版本" | Minecraft **年份+序号**主版本变化，当前节奏≈季度发布；不含 datapack/resource pack 格式号内部的 patch 变化 |
| "落后2个大版本" | ≈半年（按当前季度发布节奏折算）；发布节奏本身如果变化，这个折算要重新算 |
| "查得到 build"（条件1，代码类分支） | Modrinth `/project/{id}/version` 用 `game_versions=[target]&loaders=[目标loader]` 过滤后，存在至少一个 `version_type=release` 的条目。**常见误用**：只看 project 页面/API 默认返回的"最新版本"字段而不显式按 `game_versions` 过滤，会把"其实已有目标版本 release、只是不是该项目全局最新版本"的候选误判为"卡在旧版本"（见 F23）。查询时必须显式传 `game_versions` 参数 |
| "查得到 build"（条件1，纯数据驱动分支） | 只查 `game_versions` 是否覆盖目标版本，忽略 loader/platform 字段 |
| "release 优先，beta/alpha 的例外条款"（条件1） | 新候选：一律要求 `release` 型态，无例外。**已在本环境实际部署、且已有一段无崩溃运行记录的既有候选**：若该项目对目标版本的所有 build 均为 `beta`/`alpha`（一个 `release` 都没有），且经查证这是该维护者的长期标签惯例（而非该版本本身不稳定的信号），可将 beta/alpha 视为作者惯例、不追溯套用字面判定，保留原状。**这个豁免只对"已实测过"的既有候选成立，不能预先套用在任何新候选身上**——"这个作者一直都这样标"这个理由只有在已经实际验证过能跑之后才成立，不能作为跳过实测的理由（对应 F26 的反面：不能用"作者惯例"代替实测，只能用实测结果反过来解释惯例） |
| "environment 检查"（条件2，仅代码类分支适用） | 查**version 层级**的 `environment` 字段，对准目标 MC 版本，而不是 project 层级。纯数据驱动分支该条件视为自动通过（不适用，非豁免） |
| "存活"（条件3） | 距今最近一次**平台自身**（Modrinth/CurseForge）release 的天数（现活跃），与"创建至今时长"是两个独立变量。**不得**用关联的代码托管平台（如 GitHub）上的 commit/push 时间代替——两者可能严重脱节（见 F24） |
| "有源码链接"（条件5） | 存在可查证的公开来源（源码仓库/wiki/issue tracker 均可，纯 Discord/社群邀请连结不算）。**这个要求不因候选是纯数据驱动内容（无编译代码）而放宽或豁免**——它的存在理由有两个：(a) 代码/内容审计（能不能查出恶意逻辑或数据），(b) 维护者可追溯性/问责（出问题时能找到人、能查变更历史）。纯数据包没有 (a) 里"藏恶意代码"的风险面，但 (b) 对它同样成立——"没有代码可藏"只说明 (a) 的权重较低，不代表整条要求都不适用（见 F29） |
| "自用 vs 分发"（条件5） | 场景参数，决定除"有源码链接"之外、是否额外要求 license 允许 redistribution。用 Nix `fetchurl`（或任何等价的"直接打包分发给多个使用者"的机制）分发的场景，永远算"打包分发"，不算自用——这是该场景参数的一种具体取值示例，每个部署要按自己的实际分发方式确认，不能想当然套用 |
| "发现" vs "通过" | 出现在候选池里 = 发现；过完1–5条 = 通过。这两者的失败原因必须分开记录 |

## 3. Boundary Conditions

| 边界情况 | 处理方式 |
|---|---|
| 目标版本刚发布，候选池当前为空 | 不是流程失败，是预期状态 |
| 仿冒/抢注 project | 靠加分项6（作者信誉/Organization）做**否决式**加权 |
| 内嵌/shaded 依赖 | **结构性盲区**，API 层面无法审计，如实标注 |
| 纯私人分发 | **结构性不可达**，接受为标准残留遗漏率 |
| 依赖图中版本区间冲突 | 条件4的递归检查测不出，标注为已知未覆盖 |
| 跨 loader 兼容层本身作为依赖 | 必须真的代入条件4检查 |
| project 同时标有"纯数据驱动"和真实 loader/platform | 退回条件4检查其声明的 required 依赖 |
| 索引平台/客户端工具自身的兼容性判定 bug | 必须直接查原始字段 |
| 用关联代码托管平台的 commit 活跃度判断维护状态 | **不可靠**：部分维护团队的真实开发不经过那个公开 repo，该 repo 停更不代表项目停止维护。条件3只认平台自身发布时间戳（F24） |
| 通过清单中多个表面独立项目实际同属一个维护主体 | 触发集中度检查（见 §1）：不自动拒绝，但须在产出物里显式标注占比（F25） |
| **同一 mod/依赖在多个互相关联的部署环境（如服务端与客户端）之间要求版本一致** | 仅因两边都声称支持同一大版本，不代表这个具体版本组合已被验证过——跨环境的具体版本搭配本身也要过一次实机验证，见 §5.1（F31） |
| **候选来自一个他人维护的成熟 modpack/整合包** | 该 modpack 只是**候选池来源**（对应 §7 渠道D），不是**验证结果**——modpack 维护者自己做过的筛选不能替代本标准条件1-5的独立复查，把"别人筛过了"当免检理由是错误的信任委托（F30） |
| **特定硬件/GPU驱动/显示合成器（compositor）相容性问题** | **不属于本标准涵盖范围**。metadata/版本/loader 层面的验证结构上无法预测这类问题，只能通过在目标机器上实机测试该环境本身发现，且结果不能跨机器直接套用——遇到这类问题时应就地记录为该机器的已知限制，不要试图把它变成一条可脚本化的筛选规则 |

## 4. Failure Taxonomy

### 4a. Metadata 层面
- **F1 声明与行为不符**：metadata 标注"服务端可选"，但实际硬编码客户端专属调用
- **F2 Tag drift**：作者代码已兼容新版本但忘记打版本标签
- **F3 Project/version 层级混淆**
- **F4 字段废弃**：使用已废弃的旧字段名

### 4b. 规则设计层面
- **F5 存活门槛误杀新 fork**
- **F6 供应链/仿冒**
- **F7 依赖版本冲突**：递归检查测不出依赖间版本区间冲突
- **F8 Loader 系统性滞后被误算成单 mod 问题**
- **F9 加分项误用为负面信号**：如"没有现成兼容包"被当拒绝理由

### 4c. 发现流程层面
- **F10 关键词偏差** / **F11 单平台孤岛** / **F12 分类标签失真** / **F13 排序榜单偏差** / **F14 改名/fork 断链** / **F15 依赖图不可见** / **F16 语言/社群孤岛** / **F17 快照 vs 滚动目标混淆**

### 4d. Project Type 分流层面
- **F18 误套 loader 检查到纯数据驱动内容**
- **F19 "纯数据驱动"标签掩盖绑定代码变体**
- **F20 复用工具衍生兼容性判定**

### 4e. 标准执行/应用层面（来自实际筛选过程中真实发生的过程性失误）
- **F21 沿用旧决策，不重新推导**
- **F22 用抽象论证代替实测比较**
- **F23 查询未按 game_versions 过滤**
- **F24 用代码托管平台活跃度代替平台自身的发布记录**
- **F25 集中度盲区**：多个表面独立的候选实际同属一个维护主体

### 4f. 跨层级验证缺口层面（本轮新增，来自真实部署事故——性质是"条件1-5各自正确但组合/层级之间出问题"，不是任何单条规则写错）
- **F26 跨 mod 资料内容冲突**：两个各自通过条件1-5的候选，其游戏内容资料（recipe/loot/tag 等）互相引用，一方的 ID 变动后合并加载时崩溃；这在结构上就不是 metadata 层面的检查能发现的问题——不存在"先判断是否有耦合、再决定要不要实测"这种前置筛选，因为未声明的耦合关系本身就是这个失败模式的定义
- **F27 打包/部署层执行环境不匹配**：候选本身的版本/loader 都对，但打包该候选的部署工具链绑定了不匹配的执行时环境（如运行时版本），metadata/hash 验证测不出来，只有实际启动会暴露——这是部署工具链的问题，不是候选选择的问题
- **F28 中间分发层数据滞后于源平台**：如果筛选流程依赖某个中间打包/分发层而非直接查源平台 API，滚动更新的真实速度上限是这个中间层自己的更新节奏，不代表源平台本身没有新版本——查询前要先确认这个中间层是否已反映最新源数据
- **F29 误将"无编译代码可藏恶意"等同于"不需要源码链接"**：条件5存在的理由有代码审计和可追溯性两个，纯数据驱动内容只是前者权重低，不代表可以整体豁免（见 §2）
- **F30 把来源渠道自身的既有筛选当作免检证明**：渠道D（modpack 反推）只提供候选池，不提供验证资格，把"别人已经筛过了"当理由跳过条件1-5复查
- **F31 跨环境版本绑定假设**：同一依赖在多个关联部署环境间要求版本一致，仅因两边都声称支持同一大版本，就假设这个具体版本组合已被验证——跨版本行为差异可能未经测试
- **F32 把加分项的量化门槛当必要条件误用**：下载量、被引用数这类软性信号只用来辅助判断、排序，不是条件1-5之外的第六道硬性关卡；仅因某候选低于建议门槛就直接排除、不看它是否已经通过条件1-5，是误用（呼应 F9，这里是量化门槛具体被误用的情境）

## 5. 必要条件（最终版，全部通过；依赖递归检查）

先做 **§-1 project_type 分流**，再按分流结果代入下表：

| # | 判据 | 对应失败模式 | 已知残留缺口 |
|---|---|---|---|
| 1 | 代码类：Modrinth 确认目标版本+loader 有 `release` 构建（**必须显式按 game_versions 过滤**），查不到时 CurseForge 兜底；已实测过的既有候选适用 beta/alpha 惯例豁免（见§2）。纯数据驱动类：只查 `game_versions` 覆盖目标版本 | F1(部分)、F2、F10、F11、F18、F20、F23、F26(部分,见§5.1) | metadata声明≠真实运行时行为，必须接实测；纯数据驱动分支不受此限 |
| 2 | 代码类：**version 层级** `environment` 排除纯客户端类取值。纯数据驱动类：自动通过 | F3、F4 | 无 |
| 3 | 距今最近**平台自身**release ≤ X天**且**落后目标版本 ≤2个大版本；`存活≥1年` 若维护者名下另有已通过条目则豁免 | F5、F8、F24 | "更新频率规律"若要脚本化需另定量化窗口 |
| 4 | 所有 `required` 依赖递归通过1–3；DFS去重，遇环或深度>N标记"需人工review" | F7(部分)、F15、F19 | 内嵌/shaded依赖不可审计；依赖版本区间求交未覆盖；跨环境版本绑定见F31 |
| 5 | 有源码链接（**不因纯数据驱动而豁免，见§2**）；若场景为打包分发，license 需允许 redistribution | F29 | "自用vs分发"需在执行前显式确认 |

### 5.1 批次实机验证（必要，但作用层级不同于条件1-5）

条件1-5验证的是**每个候选各自的资格**（metadata 层面）；本节验证的是**这批候选合在一起、在目标环境里能不能真的跑起来**——两者不能互相替代，这是本轮从真实部署事故里补回来的一条硬性要求：

- **规则**：任何一轮新增/替换/移除操作，不论候选之间是否被识别出存在耦合关系，最终都必须经过一次实际启动测试（服务端：进程成功起来且日志无崩溃/无 `FormattedException` 类错误；客户端：能正常进入游戏），才能视为该轮筛选完成。
- **为什么不能靠"先判断有没有耦合再决定要不要测"**：F26 的定义就是"未声明的耦合关系"——如果耦合是可以提前从 metadata 判断出来的，它就不会是这个失败模式了。等待"先识别风险再决定要不要测"本身就是一个不成立的策略。
- **这条同时覆盖 F26（内容数据冲突）、F27（部署层环境不匹配）、F31（跨环境版本组合未验证）**——三者的根因不同，但都只能通过"实际跑一次"暴露，条件1-5在设计上就到不了这一层。
- **适用范围**：服务端与客户端一视同仁，不因为"是玩家自己选的版本""是来自受信任来源"而跳过。

## 6. 加分项

| # | 判据 | 说明 |
|---|---|---|
| 6 | 同一维护团队/组织，或维护者名下有其他已通过项目 | 优先用平台的组织功能。**注意与 §3/F25 的区别**：本条评价单个项目"是否可信"（正面），集中度检查评价整个清单"是否脆弱"（负面）——同一事实，方向相反，不要混用同一套权重 |
| 7 | 被使用/依赖的 modpack 数量 | **不用**"是否已有现成整装兼容包"当拒绝理由（F9）；这条是"被多少 modpack 引用"的计数，跟 F30（把 modpack 自己的筛选当免检证明）是完全不同的两件事——一个是加分信号，一个是免检误用，不要因为在意 F30 就连这条加分项也否定掉 |
| 8 | 无审核举报记录 + 供应链信誉检查 | 用来防 F6。仍是"搜索+人工判断"，不包装成机械核验 |
| 9 | 下载量门槛：主力 mod/数据包 >1000万，附属性质的扩展 mod/小组件（通常依赖某个主力项目、单独功能范围窄）>100万 | **标准默认值为建议门槛，非 §5 必要条件**——单独低于门槛不能当拒绝理由（见 F9/F32）。**具体部署可以显式选择把本条升级为该部署自己的强制门槛**，只要在该部署自己的文档里明示这个选择、注明生效日期，这个升级只对该部署生效，不回溯改写本标准其他使用者的默认立场。**升级为强制门槛时，必须对"已通过本条件的候选的 required 依赖"设豁免**——依赖项目自身的下载量往往远低于依赖它的主力项目（下载来源被上游吸收），单独套用门槛会出现"为了满足门槛移除依赖，反而连带打掉一个远高于门槛的主力项目"这种逻辑倒置；豁免范围仅限于"当前仍被至少一个已通过条件的候选依赖"的依赖项目，该依赖若同时也是可独立使用的候选、且没有任何东西依赖它了，仍要回头单独套用门槛。具体数值会随生态规模成长而过时，每次套用前应按目标平台当下的下载量分布重新校准，不能把某次查证时的绝对数字当成永久基准 |

## 7. 发现流水线——动态渠道分配（职责单一，重叠显式）

| 渠道 | 单一职责 | 破解的失败模式 | 操作 |
|---|---|---|---|
| **A. Facet 枚举**（非关键词） | 穷尽平台分类空间，含纯数据驱动类别 | F10, F13 | API 直接按 facets 翻页，project_type 分开跑 |
| **B. 依赖图逆向遍历** | 挖出被动关联、不主动描述自己的项目 | F15, F19 | 对每个通用库项目查其 dependents/relations 列表 |
| **C. 作者/组织图遍历** | 挖出同作者低曝光副项目，同时是集中度检查的数据来源 | F14, 与加分6互为验证 | 对通过筛选的每个项目，拉出该作者/组织名下全部项目重新走一遍规则 |
| **D. Modpack 反推** | **只提供候选池，不提供验证资格**——白嫖已有的组合灵感，但清单里每一项仍要独立跑完条件1-5+§5.1，不能因为"这份 modpack 本身筛过了"就跳过复查（对应 F30，这是本轮从真实事故里补回来的强调） | F13，长尾覆盖 | 找目标版本/玩法对齐的成熟 modpack，把完整项目列表拉出来当候选池，逐一重新验证 |
| **E. 平台外聚合** | 捕获未上架/刚起步项目 | F11, F16 | 代码托管平台按相关 topic 搜索——**仅用于发现，不用于判断存活**（F24） |
| **F. 语言维度** | 捕获非英语社区独占/优先发布的项目 | F16 | 用维护者/使用者常用的其他语言单独跑一轮 |

**重叠是故意的**：A 与 D 大概率命中同一批热门项目——若 D 命中而 A 没命中，说明 A 的分类关键词有缺口。

| **跨层级验证发现（本轮）** | 候选/loader 版本层面都对，但打包该候选的部署工具链本身有执行环境不匹配的问题 | §10 补充说明；F27（不进入必要条件，因为这是部署工具链问题，不是候选选择问题，但 §5.1 的实机测试能检测到它的症状） |
| **跨层级验证发现（本轮）** | 筛选流程如果依赖中间分发层的静态数据，其更新节奏可能滞后于源平台本身 | §10 补充说明；F28 |
| Criterion validity？（本轮） | 条件5"有源码链接"曾被理解为可因"无编译代码"而对纯数据驱动内容豁免——但该条件有审计+可追溯两个理由，后者对纯数据也成立 | 强化 §2/§5 条件5定义；F29 |
| Coverage gap？（本轮） | 客户端 mod 曾被区分成不同审查宽松度（含对整合包"信任委托、不重新查证"），造成实质上未验证的候选被当作已验证 | 明确"服务端客户端同一套必要条件"，强化§7渠道D描述禁止把渠道来源当免检证明；F30 |
| Coverage gap？（本轮） | 同一依赖在服务端/客户端等多个环境间要求版本一致，但两边"都支持某个大版本"不代表这个具体版本组合本身被验证过 | 新增 §3 边界条件；F31 |

| **Criterion addition（v1.5）** | 需要一个量化的社群采用度参考值（下载量），但如果放进 §5 必要条件会变成硬性关卡，跟既有的 F9（不能用"没有现成兼容包"当拒绝理由）精神冲突，也会让已经通过条件1-5、单纯下载量较低的既有候选被追溯判定不合格 | 放进 §6 加分项（新增第9条：主力项目建议>1000万、附属性质的扩展 mod/小组件建议>100万），明确标注"非必要条件"；新增 F32 防止这条被误用成事实上的第六道必要条件 |
| **Criterion clarification（v1.6）** | 某具体部署（本文件对应的部署）明确要求把 §6 第9条从建议值升级为该部署自己的强制门槛，这是一个合法的、显式的执行选择，不是误用 F32 想防的那种"随手拿来当挡箭牌"——但标准原文没有开放这个升级路径，字面上只能靠 F32 挡掉 | 修订条件9措辞，明确允许具体部署显式选择将其升级为强制门槛，前提是在该部署自己的文档里注明生效日期、且这个升级不回溯改写标准对其他使用者的默认立场；F32 的适用范围收窄为"未经明示声明、想当然套用"的情形 |
| **Coverage gap（v1.7）** | 把下载量门槛真的当强制门槛套用后，发现两个已通过候选的 required 依赖自身低于门槛——依赖的下载量天然会远低于依赖它的主力项目（下载来源被上游吸收），若不加区分地套用门槛，会出现"为了满足门槛移除一个依赖，反而连带打掉一个远高于门槛的主力项目"的逻辑倒置 | 条件9新增依赖豁免条款：仍被至少一个已通过候选依赖的依赖项目豁免门槛；该依赖若同时可独立使用且已无人依赖，仍要回头单独套用门槛，不是永久豁免 |

## 10. 运行节奏

绑定目标游戏的发布节奏：每次大版本发布后，

1. 立即跑一次基线（预期候选池接近空，属正常状态）
2. 之后定期重跑渠道A/B/D + 必要条件1–5，直到候选池收敛
3. 每次大版本发布后做一轮§8召回率抽样
4. **确认查询的是源平台本身，而非某个中间分发层的缓存/静态数据**——中间层的更新节奏可能落后于源平台，"这个中间层还没有新版本"不等于"源平台还没有新版本"（F28）
5. **每次切换目标版本的打包配置时，额外确认部署工具链自身的执行环境前提（如运行时版本）是否也需要同步调整**——这一步不属于条件1-5的验证范围，但如果跳过，会在 §5.1 的实机测试阶段才暴露，且不会在纯粹的构建/hash验证阶段报错（F27）
6. 完成上述步骤后，执行 §5.1 批次实机验证，确认无误后才算本轮滚动更新完成

## 11. 附录（非规范性示例，2026-09-28 快照）

**本节内容不是标准的一部分**，会随时间失效。**标注来源**：未特别说明的条目为本 session 独立查证；标为"用户报告"的条目来自用户在实际筛选/部署中的观察，本 session 未独立复核其具体数值，只吸收其暴露出的通用规则。

- **§0 场景举例**：2026年9月发布的最新 Minecraft 大版本发布后第8天，某 Forge 系 loader 仍在 beta，另一 loader 的 API 几天内即稳定。
- **§-1 数据包替代方案案例（用户报告）**：某个多方块/世界生成扩展 mod 落后目标版本，功能定位相近的纯数据包世界生成扩展因为走 §-1 左列判据（只需 `game_versions` 匹配）反而更快跟上目标版本。
- **§2/条件1 beta/alpha 惯例案例（用户报告）**：某个已部署、长期运行无崩溃的工具类 mod，其在 Modrinth 上所有历史版本（上百个）从未标过 `release`，全部是 `beta`——查证确认是该作者的长期标签习惯，不是版本不稳定的信号，套用惯例豁免保留；新候选不适用此豁免。
- **§2/F23 查询过滤陷阱案例（用户报告）**：一个高人气实用类 mod 在未按 `game_versions` 过滤的查询下被误判为卡在旧版本，过滤后确认存在目标版本的干净 release。
- **§3/F24 GitHub信号失真案例（用户报告）**：几个数据包类项目的公开 GitHub repo 早已停止更新，但同期在 Modrinth 上仍持续发布新 build，说明真实开发流程不经过那个公开 repo。
- **§3/F25 集中度案例（用户报告）**：几个表面独立的数据包项目经查同属一个工作室；条件5收紧后移除一批无源码项目，副作用是同时清空了另外两组集中度风险，纯属条件5执行的连带效果，不是刻意针对集中度做的调整。
- **§5条件5/F29 案例（用户报告）**：一批纯数据包项目（结构/地牢扩展类）因为只有 Discord 邀请连结、没有可查证的公开源码仓库/wiki/issue tracker，按强化后的条件5判定移除——此前的执行对纯数据驱动内容留了"无代码可藏所以没差"的宽松空间，此次收紧后不再豁免。
- **§5.1/F26 跨mod数据冲突案例（用户报告）**：两个内容 mod（其一是生存类 QoL mod、另一是生物群系扩展 mod）分别都通过条件1-5，但前者内建的"市集交易"配方数据引用了后者的物品 ID，而该 ID 在当前版本的后者里已改名/移除——两个 mod 各自的 metadata 完全正常，服务器启动时因数据包合并失败直接拒绝启动，只有实际启动测试才发现。
- **§5.1/F31 跨环境版本绑定案例（用户报告）**：客户端叠加某个内容 mod 的对应版本时，未同步核对该 mod 在当前版本下新增的必要依赖（此前版本没有这个依赖），实际启动时因缺少依赖直接报错——metadata 查证时若未重新拉取该候选当前版本的完整依赖列表，只沿用旧版本的依赖表，就会漏掉这类新增依赖。
- **§10/F27 部署层案例（用户报告）**：某 Nix 生态的打包工具（针对某 loader 的 server derivation）未显式绑定与目标 Minecraft 版本匹配的 Java 运行时，构建/hash 验证阶段完全不报错，只有实际启动 JVM 才会报运行时版本不兼容的错误；且该错误未必会出现在标准的进程日志捕获路径里，需要额外手段（如直接附加到运行中的会话）才能看到报错内容。这类问题的修法通常是在打包配置里显式覆盖运行时依赖，且每次升级目标版本都要重新确认这个覆盖是否仍然必要（上游可能修复默认行为，也可能提高运行时版本要求）。
- **§10/F28 中间分发层案例（用户报告）**：某些 loader 的版本兼容表由上游仓库的每日自动化流程重新生成并提交，本地滚动更新流程如果只等"上游生态本身有没有新版本"，会忽略这个中间表自己的更新延迟——真正决定本地能不能用上新版本的，是这个中间表有没有先更新。
- **§6 条件8 威胁模型参照**：2023年 Fractureiser 事件——恶意代码通过被盗的作者账号注入，经由主流 mod 分发平台传播到多个热门 Forge/Fabric mod。
- **§-1/§3/F20 平台层 bug 案例**：Modrinth 官方帮助中心说明"数据包"在其 Platforms 体系里是独立于各 mod loader 的平台标识（来源：[Modrinth Help Center](https://support.modrinth.com/en/articles/14030919-datapacks-on-modrinth-hosting)）；官方仓库存在一个截至查证时仍未修复的公开 issue，客户端 App 把"数据包"当作外来 platform 类型处理导致虚假不兼容警告（来源：[modrinth/code#3538](https://github.com/modrinth/code/issues/3538)）。
- **§3 硬件相容性边界案例（用户报告）**：某光影类客户端 mod 与特定 GPU 多卡切换模式（PRIME offload）+ 特定 Wayland compositor 的组合实测崩溃（原生 GL context 建立失败），换成同一台机器上的纯净对照实例可正常启动，排查确认是该 mod 与这个具体硬件/合成器组合不相容，与 mod 本身的版本/loader 相容性无关，也不代表其他机器会遇到同样问题——按 §3 判定为标准范围外，就地记录为该机器的已知限制即可，不追加为通用规则。
